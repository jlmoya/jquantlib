# C++ QuantLib v1.42.1 → v1.43 migration — progress

**Ground truth:** C++ QuantLib `v1.43` @ `6b57206e04598f092efee66e3b367efc84771995`
(previous pin: `v1.42.1` @ `099987f0ca2c11c505dc4348cdb9ce01a598e1e5`).

Both ports move together: **JQuantLib** (Java, this repo) and **PQuantLib**
(Python, `~/Projects/PycharmProjects/pquantlib`). Target release version
`1.43.0` in both.

Removals in C++ are followed, but the removed API is kept and marked
`@Deprecated` in Java / `warnings.deprecated` in Python rather than deleted.

## Status

### Phase 0 — re-pin and re-baseline ✅

Submodule re-pinned to v1.43, all references regenerated, suite green.

Seven silent harness defects were found and fixed while doing it — worth
recording because each had been producing plausible-looking output:

1. The Jaeckel Sobol probe was **non-deterministic**: three runs of the same
   binary gave three different hashes. Root cause was a 32-dimension table
   queried at dimension 33, combined with entropy seeding when `seed == 0`.
2. Two probes had **never compiled** since being written.
3. A **stale binary** with no CMake target, no source and no git history was
   still being run by the generator, corrupting 13 reference keys. It was
   ABI-linked against "current version 1.42.0".
4. `cluster_w8d` **wrote its reference file and also logged to stdout**; the
   generator's redirect then clobbered the file.
5. One probe printed **uninitialised memory** (`e-316` denormals in
   `cluster/l10b.json`) — flagged, not yet fixed.
6. Five probes failed to compile after the re-pin because v1.43 dropped
   `YoYInflationIndex`'s `bool interpolated` argument.
7. JQuantLib had **no calendar reference at all**, so calendar drift was
   structurally invisible. A 44-calendar probe now closes that gap.

## Defects found in the ports (not in v1.43)

Each of these was pre-existing and silent — the suite was green with all of
them in place.

| # | Where | What |
|---|---|---|
| 1 | `CashFlows.startDate` | Cast every element to `Coupon` unconditionally, so it threw on any leg holding a plain cashflow — exactly the shape a cross-currency leg takes once its notional exchanges are attached. C++ has used a checked cast since well before v1.42.1. |
| 2 | `CashFlows.maturityDate` | Used the payment date for coupons; C++ uses the accrual end date. These differ whenever a payment lag or calendar adjustment moves the payment past the accrual end. |
| 3 | `Swap.legBPS/legNPV/startDiscounts/endDiscounts` | Guarded with `!Double.isNaN(x)` against a `Double.MAX_VALUE` null sentinel, so the guard could never fire and a null result was returned as `1.8e308`. |
| 4 | `IterativeBootstrap` | No notion of `latestRelevantDate`: the curve stops at its last pillar, where C++ extends it to the furthest date any helper actually needs. Latent until (2) was fixed, then surfaced as a bootstrap failure on OIS helpers with a payment lag. |
| 5 | `SouthAfrica.name()` | Returned `"SouthAfrica"`, C++ returns `"South Africa"`. |
| 6 | `Israel` SHIR | Friday+Saturday weekend; C++ `ShirImpl` derives from `WesternImpl`, i.e. Saturday+Sunday. Wrong in v1.42.1 too, and live in the published artifact. |
| 7 | `Israel` | The `Telbor` market was missing entirely. |
| 8 | Harness references | Four reference files were still pinned to v1.42.1 long after the re-pin, so four test groups were being cross-validated against the *old* C++. Three distinct causes: two probes hardcoded the version string instead of reading `QL_VERSION`; one probe's source had been rewritten but never re-run, leaving a reference whose case names no longer existed; and `pricingengines/capfloor/blackcheck.json` is an orphan — no probe source, no consumer, committed by accident after three phase plans had noted it as stray untracked noise. |
| 9 | `IntegralHestonVarianceOptionEngine` | Java had deliberately relaxed C++'s dividend-yield guard, with a comment stating that "the Java `HestonProcess` does not accept an empty handle". It does. The guard is now ported, and its own probe case proves a flat-*zero* curve is still rejected — the requirement is on the handle being empty, not on the yield being zero. |

| 10 | `HullWhite.generateArguments` | Never refreshed `r0` when the term structure relinked, so every quantity derived from it silently used a stale rate. The Java class documented the omission as a caveat; C++ has always refreshed it. |
| 11 | `Vasicek.A` | Returned `0.0` in the small-mean-reversion branch, pricing **every** zero bond at exactly zero. C++ returns the analytic limit. |
| 12 | `CubicInterpolation` (Akima) | No minimum-points guard: three-point Akima died with an array-index error from inside the derivative loop instead of saying what was wrong. |
| 13 | `Option.Greeks.reset` | Reset the greeks to `NaN` while every "did the engine provide this?" guard compared against `NULL_REAL`, so `delta()` on an engine that populates no greeks returned `NaN` instead of refusing. Same mixed-sentinel bug as (3). |
| 14 | `DiscreteSimpsonIntegral` | On an empty array the even-`n` trailing term indexed `x[-1]`. |
| 15 | `FastFourierTransform` | Rejected order 0, so a size-1 transform was impossible — even though `minOrder(1)` returns 0 and hands you exactly that. |
| 16 | `IterativeBootstrap` | The duplicate-pillar check compared `Date` objects by **reference**, so it had never fired once. |
| 17 | `Sofr` | Used `UnitedStates.GOVERNMENTBOND`; C++ uses `UnitedStates::SOFR`. Good Friday is a SOFR fixing holiday but a Fed business day, so every value-date schedule was subtly wrong. |
| 18 | `OvernightLeg` | Missing C++'s `WeekendsOnly` payment-calendar fallback, so a weekend-stub coupon's payment date went unadjusted. |

The Java-side pattern worth noticing in 1–4, 9 and 10: each was a small,
locally reasonable accommodation ("Java can't express this", "the engine
ignores it anyway", "Java has no separate pillar date") that was never checked
against the C++ it was accommodating. Several were documented *as* caveats —
which made them look considered rather than unverified.

## Known gaps, recorded rather than hidden

- **PQuantLib overnight modifiers.** `OvernightIndexedCoupon` implements none
  of `compoundSpreadDaily` / `lookbackDays` / `observationShift` /
  `lockoutDays` / `averagingMethod` / `telescopicValueDates`. The
  cross-currency basis swap keeps the C++ signature but raises
  `NotImplementedError` on a non-default value rather than pricing as if the
  flag were off. Closing this needs the coupon itself ported further.
- **`cluster/l10b.json`** (PQuantLib) contains uninitialised-memory denormals
  from a probe that reads past its buffer. Flagged, not yet fixed.
- **Two PQuantLib probes have never compiled** (`cluster_l7d` curve
  constructors, `cluster_l8a` helper).
- **`generate-references.sh` has no orphan-binary guard**: it runs whatever is
  in `cpp/build/probes/`, including binaries whose source is gone. This has
  already corrupted a reference once.
- **`MixedLinearCubicInterpolation`** allowed a switch index one past the end
  under `ShareRanges` (fixed), but the same guard needs checking in PQuantLib.
- **`testInterpolateWithoutUpdate` has no Java equivalent, by construction.**
  It exercises C++'s `detail::interpolateWithoutUpdate`, a SFINAE helper that
  detects whether an interpolator's `interpolate` accepts a trailing
  `bool update` and skips the initial update if so. Java's `Interpolator`
  has one signature and its interpolations update in the constructor, so there
  is nothing to detect and nothing to skip. Recorded as not-applicable rather
  than as an omission — the behaviour the C++ test protects (a caller getting
  a not-yet-updated interpolation) cannot arise here.
- **A latent flaky *hang* in the Java suite.** Under load, changing the global
  evaluation date can fan out to stale `OISRateHelper` instances left
  registered by earlier test classes; those rebuild schedules through
  `Calendar.advance`, whose holiday-skip loop is unbounded. Observed once as a
  13-minute spin on `AsianOptionTest`, with the same class taking 0.9 s and
  34.5 s on other runs of identical sources — the difference is GC timing,
  since observers are held weakly. Two contributing weaknesses, neither
  addressed yet: the unbounded loop in `Calendar.advance`, and test classes
  leaving live rate helpers registered on the global evaluation date. Fixing
  the first is a main-source behavioural change and needs its own
  C++-cross-validated task.
- **`ConstNotionalCrossCurrencySwapRateHelper`'s v1.43 rewrite** is not ported:
  upstream now builds a real `ConstNotionalCrossCurrencyFixedVsFloatingSwap`
  priced by the new engine and returns `fairRate()`. Both now exist in Java, so
  this is unblocked; its three cases in `CrossCurrencyRateHelpersTest` will need
  re-baselining when it lands.
- **`InterpolatedDiscountCurve.discountImpl`** extrapolates by interpolation
  rather than C++'s explicit flat-forward branch. Equivalent under `LogLinear`
  (the piecewise default), divergent for `Cubic`/`LogCubic`/`Linear`-on-DF.
  Latent before, and more reachable now that the bootstrap extends curves past
  their last pillar.

## Upstream defect observed in v1.43

`PearsonSpreadEngine::calculate`'s `effectiveStrike <= 0` branch returns the
**call** intrinsic regardless of `optionType`. For a sufficiently negative
strike a put therefore picks up a non-zero value where zero is correct, and
put-call parity breaks. Upstream's own test uses strike 5 and never reaches
the branch.

Ported bug-for-bug — C++ is the oracle, and diverging would make the two
libraries disagree — and pinned by dedicated probe cases
(`pearson_a_put_km10_*`, `pearson_a_put_km30_*`) so the behaviour is explicit
rather than accidental. Not reported upstream yet.
