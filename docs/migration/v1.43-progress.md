# C++ QuantLib v1.42.1 → v1.43 migration — progress

**Ground truth:** C++ QuantLib `v1.43` @ `6b57206e04598f092efee66e3b367efc84771995`
(previous pin: `v1.42.1` @ `099987f0ca2c11c505dc4348cdb9ce01a598e1e5`).

Both ports move together: **JQuantLib** (Java, this repo) and **PQuantLib**
(Python, `~/Projects/PycharmProjects/pquantlib`). Target release version
`1.43.0` in both.

Removals in C++ are followed, but the removed API is kept and marked
`@Deprecated` in Java / `warnings.deprecated` in Python rather than deleted.

## Status

### Phase 0 — re-pin and re-baseline ✅

Submodule re-pinned to v1.43, all references regenerated, suite green.

Seven silent harness defects were found and fixed while doing it — worth
recording because each had been producing plausible-looking output:

1. The Jaeckel Sobol probe was **non-deterministic**: three runs of the same
   binary gave three different hashes. Root cause was a 32-dimension table
   queried at dimension 33, combined with entropy seeding when `seed == 0`.
2. Two probes had **never compiled** since being written.
3. A **stale binary** with no CMake target, no source and no git history was
   still being run by the generator, corrupting 13 reference keys. It was
   ABI-linked against "current version 1.42.0".
4. `cluster_w8d` **wrote its reference file and also logged to stdout**; the
   generator's redirect then clobbered the file.
5. One probe printed **uninitialised memory** (`e-316` denormals in
   `cluster/l10b.json`) — flagged, not yet fixed.
6. Five probes failed to compile after the re-pin because v1.43 dropped
   `YoYInflationIndex`'s `bool interpolated` argument.
7. JQuantLib had **no calendar reference at all**, so calendar drift was
   structurally invisible. A 44-calendar probe now closes that gap.

## Defects found in the ports (not in v1.43)

Each of these was pre-existing and silent — the suite was green with all of
them in place.

| # | Where | What |
|---|---|---|
| 1 | `CashFlows.startDate` | Cast every element to `Coupon` unconditionally, so it threw on any leg holding a plain cashflow — exactly the shape a cross-currency leg takes once its notional exchanges are attached. C++ has used a checked cast since well before v1.42.1. |
| 2 | `CashFlows.maturityDate` | Used the payment date for coupons; C++ uses the accrual end date. These differ whenever a payment lag or calendar adjustment moves the payment past the accrual end. |
| 3 | `Swap.legBPS/legNPV/startDiscounts/endDiscounts` | Guarded with `!Double.isNaN(x)` against a `Double.MAX_VALUE` null sentinel, so the guard could never fire and a null result was returned as `1.8e308`. |
| 4 | `IterativeBootstrap` | No notion of `latestRelevantDate`: the curve stops at its last pillar, where C++ extends it to the furthest date any helper actually needs. Latent until (2) was fixed, then surfaced as a bootstrap failure on OIS helpers with a payment lag. |
| 5 | `SouthAfrica.name()` | Returned `"SouthAfrica"`, C++ returns `"South Africa"`. |
| 6 | `Israel` SHIR | Friday+Saturday weekend; C++ `ShirImpl` derives from `WesternImpl`, i.e. Saturday+Sunday. Wrong in v1.42.1 too, and live in the published artifact. |
| 7 | `Israel` | The `Telbor` market was missing entirely. |

## Upstream defect observed in v1.43

`PearsonSpreadEngine::calculate`'s `effectiveStrike <= 0` branch returns the
**call** intrinsic regardless of `optionType`. For a sufficiently negative
strike a put therefore picks up a non-zero value where zero is correct, and
put-call parity breaks. Upstream's own test uses strike 5 and never reaches
the branch.

Ported bug-for-bug — C++ is the oracle, and diverging would make the two
libraries disagree — and pinned by dedicated probe cases
(`pearson_a_put_km10_*`, `pearson_a_put_km30_*`) so the behaviour is explicit
rather than accidental. Not reported upstream yet.
