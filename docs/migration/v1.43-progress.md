# C++ QuantLib v1.42.1 → v1.43 migration — progress

**Ground truth:** C++ QuantLib `v1.43` @ `6b57206e04598f092efee66e3b367efc84771995`
(previous pin: `v1.42.1` @ `099987f0ca2c11c505dc4348cdb9ce01a598e1e5`).

Both ports move together: **JQuantLib** (Java, this repo) and **PQuantLib**
(Python, `~/Projects/PycharmProjects/pquantlib`). Target release version
`1.43.0` in both.

Removals in C++ are followed, but the removed API is kept and marked
`@Deprecated` in Java / `warnings.deprecated` in Python rather than deleted.

## Status

### Phase 0 — re-pin and re-baseline ✅

Submodule re-pinned to v1.43, all references regenerated, suite green.

Seven silent harness defects were found and fixed while doing it — worth
recording because each had been producing plausible-looking output:

1. The Jaeckel Sobol probe was **non-deterministic**: three runs of the same
   binary gave three different hashes. Root cause was a 32-dimension table
   queried at dimension 33, combined with entropy seeding when `seed == 0`.
2. Two probes had **never compiled** since being written.
3. A **stale binary** with no CMake target, no source and no git history was
   still being run by the generator, corrupting 13 reference keys. It was
   ABI-linked against "current version 1.42.0".
4. `cluster_w8d` **wrote its reference file and also logged to stdout**; the
   generator's redirect then clobbered the file.
5. One probe printed **uninitialised memory** (`e-316` denormals in
   `cluster/l10b.json`) — flagged, not yet fixed.
6. Five probes failed to compile after the re-pin because v1.43 dropped
   `YoYInflationIndex`'s `bool interpolated` argument.
7. JQuantLib had **no calendar reference at all**, so calendar drift was
   structurally invisible. A 44-calendar probe now closes that gap.

### Phase 5b — PQuantLib coverage gate 🔄

The Python gate was reporting 51.8% raw coverage (985 unflagged of 2045). That
number was defended in `docs/carve-outs.md` as deliberate, and the defence did
not survive checking: of its two structural claims, one asserted a currency
registry that did not exist (103 currencies were simply absent) and the other
described the pricingengines/math gap as "dominated by nested-helper and
`detail::` names" when it is 94% and 85% genuine top-level classes — 890 of the
985 repo-wide. Both are struck through in place rather than deleted, and the
rest of that document is marked unverified until re-checked.

The gate has been given JQuantLib's semantics: a class is either ported or
allowlisted with a one-line rationale, and DONE means `UNFLAGGED == 0`. The
allowlist started empty on purpose and holds three entries. The rule is written
into the script's own docstring, because it is the part that decays first:

> "We haven't got to it yet" is not a rationale. A coverage gate that can be
> silenced by intent is not a gate.

Method: waves of subagents in isolated git worktrees, one subsystem each,
porting against C++ v1.43 with probes and cross-validated tests, with
`pytest` / `ruff` / `pyright` green before every commit. Each wave is merged,
the gate re-run, and the full suite re-verified before the merge is pushed — so
the number only moves on verified, suite-green work.

| 2 | indexes | 96 | 1 | ✅ merged |

Every wave so far has found defects in already-"ported", already-green code.
The math wave found ten. Two are worth recording here because they share a
shape with the twenty-three below — a delegation to a third-party library that
was never checked against the reference:

- **`Burley2020SobolRsg` was not Burley 2020.** It was scipy's Matousek LMS +
  shift. Its own docstring conceded it was not bit-identical to C++, and it was
  tested only on statistical properties, never against the reference. Now a

- **`Ranlux3UniformRng` mapped seed 0 to 1**, attributed to a libstdc++
  fallback. The standard specifies `default_seed = 19780503`, and the probe
  confirms seed 0 and 19780503 produce the same stream in C++.

## Defects found in the ports (not in v1.43)

Each of these was pre-existing and silent — the suite was green with all of
them in place.

| # | Where | What |
|---|---|---|
| 1 | `CashFlows.startDate` | Cast every element to `Coupon` unconditionally, so it threw on any leg holding a plain cashflow — exactly the shape a cross-currency leg takes once its notional exchanges are attached. C++ has used a checked cast since well before v1.42.1. |
| 2 | `CashFlows.maturityDate` | Used the payment date for coupons; C++ uses the accrual end date. These differ whenever a payment lag or calendar adjustment moves the payment past the accrual end. |

## 24. Tests that passed by luck — the leaked global evaluation date

Found during the PQuantLib coverage programme, and recorded separately from the
twenty-three above because it is not one wrong number but a whole category of
tests that were not testing what they claimed.

**Thirteen PQuantLib test files never pinned the global evaluation date**, while
the C++ probes they assert against all do. With no pin, the engines fall back to
the machine's wall clock to decide which flows have already occurred. The CDS
case measured directly:

```
eval date unset (wall clock 2026-08-05)   npv = -377723.22942520987
eval date = 15 Jun 2026 (the probe's)     npv = -363343.23299626424
reference (cluster_l8b.json)              npv = -363343.2329962641
```

These tests were green. They were green because `ObservableSettings` is global
and other modules set the evaluation date without resetting it, so in a
full-suite run the affected modules inherited a usable date from whoever ran
before them. Run alone, they fall back to the wall clock and fail. The failure
is therefore **order-dependent and date-dependent**, which is the worst
combination: it does not reproduce on demand, and it arrives on a calendar date
nobody chose.

Confirmed pre-existing by A/B against a pristine `git archive HEAD` overlay —
pristine and live produce byte-identical failures, so nothing in the working
tree caused it.

Affected, each now carrying an autouse fixture that pins the probe's date and
resets it in teardown, with the probe file and line cited inline:

| File | Probe | Date |
|---|---|---|
| `test_credit_default_swap.py` (12) | `cluster_l8b/probe.cpp:64` | 15 Jun 2026 |
| `test_vanilla_swap.py` (5), `test_make_swap_factories.py` (2), `test_swap_rate_helper.py` (1) | `cluster_l3c/probe.cpp:47` | 17 Jan 2024 |
| `test_black_capfloor_engine.py` (3), `test_cap_helper.py` (1) | `cluster_l4e/probe.cpp:71` | 17 Jan 2024 |
| `test_basismodels.py` (1) | `cluster_w8a/probe.cpp:82` | 15 Jan 2024 |

This also explains the "9 order-dependent credit-default-swap tests" recorded
under known gaps: same root cause, now fixed rather than tolerated.

**Two related findings from the same investigation:**

- `MakeCDS` defaults `lastPeriodDayCounter` to `Actual360(include_last_day=True)`
  (`makecds.hpp:83`), and C++ threads it into the leg
  (`creditdefaultswap.cpp:102-107`). PQuantLib discarded it — `del
  last_period_day_counter  # not yet wired into fixed_rate_leg builder` — so a
  manual CDS passing `None` and the factory agreed by accident. Wiring it up
  made them legitimately differ by one accrual day. The fix gave the manual CDS
  the factory's convention rather than editing the expected number, so the test
  still asserts "same inputs ⇒ same price" and now actually tests something.
- `test_cms_leg_capped_raises` asserted that capped CMS legs raise, on a guard
  whose comment said "deferred to W12-B". `CappedFlooredCmsCoupon` already
  existed and C++ `CmsLeg` dispatches capped periods to it
  (`cmscoupon.cpp:162-176`). Another stale caveat outliving its premise — the
  same shape as most of the twenty-three.

**Open question for the Java port.** JQuantLib has the same global
`Settings().evaluationDate()` with the same wall-clock fallback, and 94 of its
195 probe-asserting test files never pin it. Whether they are genuinely
date-independent or merely inheriting leaked state is being settled by running
the suite with a fresh JVM per test class, which removes all cross-class
leakage. Result to be recorded here.

## Coverage gate: closing the last 19

The gate (`migration-harness/check_coverage.py`) had read **0 unflagged** and
that had been recorded as 100% functional coverage. It was wrong, and how it was
wrong is the point: the `CPP_DECL` regex required a line to *begin* with
`class`/`struct` and to have `:`/`{`/end-of-line straight after the name, so it
never saw one-line `template <...> class X final : ...`, `class X final`, or a
leading macro. **72 C++ classes were missing from the denominator entirely.** A
name the gate cannot see can never be reported missing, so it read zero while
classes were absent. Denominator 2045 → 2117 → 2112 after also stripping `/* */`
block comments. 53 of the 72 turned out to be already ported; the remaining 19
were closed here.

**4 ported, 15 allowlisted-with-evidence, gate now 0 unflagged at 100.0%.**

An allowlist entry qualified only when all three held, and each rationale states
them: the C++ declaration shows the name is nested / private / a tag type / a
`detail::` template rather than user-constructible; a named Java construct
subsumes it; and the behaviour it carries is cross-validated against C++ in a
named test. "It looks like a nested helper" was not accepted — the third
condition is what turned three of these into new work.

Two notes on the probes, both learned the hard way:

- **Floating-point contraction is a probe hazard.** The first Lagrange grid used
  `-1.0 + 0.2*i`, which clang contracts to an `fma` and lands node 5 on
  `5.55e-17` instead of `0`. The barycentric *derivative* next to such a node is
  catastrophic-cancellation territory, so the emitted number recorded the
  compiler's contraction choice rather than QuantLib's arithmetic — and the Java
  side, doing strict IEEE, disagreed by the whole value. The grid now uses
  `i / 5.0`; a division cannot be fused.
- **Pick query points where the quantity is determined.** The vanna-volga smile
  ends in `blackFormulaImpliedStdDev`, whose solve stops at 1e-6 *on the price*;
  beyond ~3 standard deviations vega collapses and the recovered volatility is
  arbitrary to several decimals. The grid is laid out in standard deviations of
  log-moneyness and stops at ±2, which still overshoots every quoted strike.

## Known gaps, recorded rather than hidden


- **PQuantLib overnight modifiers.** `OvernightIndexedCoupon` implements none
  of `compoundSpreadDaily` / `lookbackDays` / `observationShift` /
  `lockoutDays` / `averagingMethod` / `telescopicValueDates`. The
  cross-currency basis swap keeps the C++ signature but raises
  `NotImplementedError` on a non-default value rather than pricing as if the
  flag were off. Closing this needs the coupon itself ported further.
- **`cluster/l10b.json`** (PQuantLib) contains uninitialised-memory denormals
  from a probe that reads past its buffer. Flagged, not yet fixed.
- **Two PQuantLib probes have never compiled** (`cluster_l7d` curve
  constructors, `cluster_l8a` helper).
- **`generate-references.sh` has no orphan-binary guard**: it runs whatever is
  in `cpp/build/probes/`, including binaries whose source is gone. This has
  already corrupted a reference once.
- **`MixedLinearCubicInterpolation`** allowed a switch index one past the end
  under `ShareRanges` (fixed), but the same guard needs checking in PQuantLib.
- **`testInterpolateWithoutUpdate` has no Java equivalent, by construction.**
  It exercises C++'s `detail::interpolateWithoutUpdate`, a SFINAE helper that
  detects whether an interpolator's `interpolate` accepts a trailing
  `bool update` and skips the initial update if so. Java's `Interpolator`
  has one signature and its interpolations update in the constructor, so there
  is nothing to detect and nothing to skip. Recorded as not-applicable rather
  than as an omission — the behaviour the C++ test protects (a caller getting
  a not-yet-updated interpolation) cannot arise here.
- **A latent flaky *hang* in the Java suite.** Under load, changing the global
  evaluation date can fan out to stale `OISRateHelper` instances left
  registered by earlier test classes; those rebuild schedules through
  `Calendar.advance`, whose holiday-skip loop is unbounded. Observed once as a
  13-minute spin on `AsianOptionTest`, with the same class taking 0.9 s and
  34.5 s on other runs of identical sources — the difference is GC timing,
  since observers are held weakly. Two contributing weaknesses, neither
  addressed yet: the unbounded loop in `Calendar.advance`, and test classes
  leaving live rate helpers registered on the global evaluation date. Fixing
  the first is a main-source behavioural change and needs its own
  C++-cross-validated task.
- **`ConstNotionalCrossCurrencySwapRateHelper`'s v1.43 rewrite** is not ported:
  upstream now builds a real `ConstNotionalCrossCurrencyFixedVsFloatingSwap`
  priced by the new engine and returns `fairRate()`. Both now exist in Java, so
  this is unblocked; its three cases in `CrossCurrencyRateHelpersTest` will need
  re-baselining when it lands.
- **`GeneralizedHullWhite.LinearFlatInterpolationAdapter` freezes its endpoint
  ordinates.** C++ reads `yBegin_[0]` and `yBegin_[n-1]` live on every call
  (`generalizedhullwhite.hpp:359-363`); the Java adapter snapshots them into
  `final double yMin/yMax` at construction. The wrapped y-buffer *is* live, so
  after `calibrate()` → `setParams` → `generateArguments()` the interpolation
  sees new ordinates while the clamps do not. Because `speedperiods_[0] == 0.0
  == xMin`, `a()` and `sigma()` — which evaluate at `t = 0` — take the
  `x <= xMin` branch and would return pre-calibration values. Latent: no test
  calibrates a `GeneralizedHullWhite`. Also `isInRange` is hardcoded `true`
  where C++'s `templateImpl::isInRange` is a real bounds check. Found while
  classifying `LinearFlatInterpolationImpl`; not fixed, because fixing it wants
  a calibration test of its own to prove the fix.
- **The XABR traits-factories are inconsistent.** `Zabr` is now ported;
  `SABR`, `NoArbSabr`, `VannaVolga` and `LinearFlat` remain allowlisted as
  C++-only tags. The repo does port traits-factories in general (`Linear`,
  `Cubic`, `BicubicSpline`, `ConvexMonotone`, `Abcd`, …), so the XABR family is
  the exception rather than the rule, and porting the other four to match is
  open work rather than a settled design. Note also that the `SABR` allowlist
  rationale was factually wrong until now — it claimed a case-rename to
  `math.interpolations.Sabr`, but `termstructures.volatilities.Sabr` ports the
  free functions of `ql/termstructures/volatility/sabr.hpp`, a different C++
  entity, and the traits-factory `SABR` has no Java counterpart at all. Matching
  on the name rather than the structure is very likely why `Zabr` was never
  classified in the first place.
- **`InterpolatedDiscountCurve.discountImpl`** extrapolates by interpolation
  rather than C++'s explicit flat-forward branch. Equivalent under `LogLinear`
  (the piecewise default), divergent for `Cubic`/`LogCubic`/`Linear`-on-DF.
  Latent before, and more reachable now that the bootstrap extends curves past
  their last pillar.

## Upstream defects observed in v1.43

Three so far. The first two are ported bug-for-bug — C++ is the oracle, and
diverging would make the two libraries disagree — and both are pinned by
dedicated probe cases so the behaviour is explicit rather than accidental. The
third is the one case where the port deliberately does *not* follow C++, for the
reason given. **None has been reported upstream yet.**

### 3. `LagrangeInterpolation` returns NaN at a node whose abscissa is zero

`ql/math/interpolations/lagrangeinterpolation.hpp:114-119`:

```cpp
const Real eps = 10*QL_EPSILON*std::abs(x);
const auto iter = std::lower_bound(this->xBegin_, this->xEnd_, x - eps);
if (iter != this->xEnd_ && *iter - x < eps) {
    return yBegin[std::distance(this->xBegin_, iter)];
}
```

The node-snap window is scaled by `|x|`, so at `x == 0` it collapses to zero and
the strict `<` can never fire. Evaluation falls through to the barycentric
quotient, where `(x - x_i) == 0` for that node divides by zero, and the value
comes back `NaN`. Any grid containing 0 — which is to say any symmetric grid,
including the equidistant Runge grid every textbook uses — is affected.

JQuantLib already diverged here before this was written down: `LagrangeInterpolation._value`
uses `<= eps`, which is exact at a zero node. That divergence is now asserted
rather than silent — `LagrangeInterpolationCrossValidationTest` skips the two
C++ `NaN` rows, asserts Java returns the tabulated ordinate instead, and
asserts the *count* of such rows, so if the divergence ever spreads beyond the
zero-abscissa node the test fails.

Found by the probe, not by reading: the value simply came back as JSON `null`.


### 2. `ZigguratGaussianRng` wedge test — misplaced parenthesis

`ql/math/randomnumbers/zigguratgaussianrng.hpp:106`:

```cpp
if (normF(i + 1) + (normF(i) - normF(i + 1) * nextReal()) < pdf(x))
```

which evaluates `f[i+1] + f[i] - f[i+1]*u`. The Marsaglia-Tsang wedge test is
`f[i+1] + (f[i] - f[i+1])*u` — the multiplication should bind to the whole
difference, not to `f[i+1]` alone.

This is not cosmetic. The threshold is shifted upward for every wedge sample,
so wedge draws are rejected far more often than they should be and the loop
re-draws. For representative adjacent layer densities (f[i] = 0.60,
f[i+1] = 0.45, pdf(x) = 0.52) the correct test accepts ~47% of the time and the
expression as written **never accepts** — the acceptance interval has moved off
the unit interval entirely. The generated stream is therefore not the intended
Gaussian.

Worth reporting upstream with priority: this affects anyone using
`ZigguratGaussianRng` for simulation.

### 1. `PearsonSpreadEngine` non-positive-strike branch

`PearsonSpreadEngine::calculate`'s `effectiveStrike <= 0` branch returns the
**call** intrinsic regardless of `optionType`. For a sufficiently negative
strike a put therefore picks up a non-zero value where zero is correct, and
put-call parity breaks. Upstream's own test uses strike 5 and never reaches
the branch.

Pinned by dedicated probe cases (`pearson_a_put_km10_*`,
`pearson_a_put_km30_*`).
